# Chapter 6: Performing Retrieval-Augmented Generation on AWS

## Core Idea
RAG grounds LLM responses in externally retrieved, up-to-date data (query → embed → retrieve top-N chunks → augment prompt → generate) rather than relying solely on static pretrained knowledge — reducing hallucination and staleness, at the cost of retrieval latency and dependence on data-source quality; on Bedrock this is built from embeddings models + vector stores (OpenSearch/FAISS) + knowledge bases + agents.

## Frameworks Introduced
- **Three-phase RAG pipeline**: Query (embed the input) → Retrieval (semantic search for top-N relevant chunks) → Generation (augment prompt with retrieved chunks, generate response).
  - When to use: any application needing current, domain-grounded, or proprietary-data-informed responses beyond the model's training cutoff.
- **RAG vs. alternatives comparison** (RAG, Search Engine, Semantic Search, End-to-End Model): differs on data freshness, output complexity, and generative capability — RAG uniquely combines retrieval AND synthesis into new, contextual text (vs. search engines returning links, semantic search returning passages, end-to-end models bound by training data).
  - When to use RAG specifically: QA, chat, doc summarization needing both freshness and synthesized answers — not simple lookups (semantic search suffices) or latency-critical real-time chat (RAG retrieval adds latency).
- **Two agent types**: single-turn function-calling agents (invoke APIs/Lambda in one interaction — e.g., processing a claim) vs. multi-turn knowledge-base agents using the **ReAct framework** (Reasoning and Acting — question → think → act → observe loop) for complex, multistep reasoning tasks.
  - When to use: function-calling for atomic, well-defined API-backed actions; ReAct/knowledge-base agents when the task requires planning, adjusting based on intermediate results, or synthesizing across multiple data sources.

## Key Concepts
- **Embedding**: vector encoding of text/query semantic meaning enabling similarity-based (not keyword) search.
- **Vector database**: specialized store for high-dimensional embeddings supporting fast similarity search (cosine similarity, Euclidean distance) — e.g., OpenSearch, FAISS, Pinecone, Milvus, Weaviate, Qdrant.
- **Chunking**: splitting documents into segments (e.g., 1,000 chars with 100-char overlap) before embedding — overlap preserves context that would otherwise be lost at chunk boundaries.
- **Knowledge base (Bedrock)**: managed repository integrating data sources (S3-backed) with automatic chunking/embedding/indexing, queried via `Retrieve` or `RetrieveAndGenerate` APIs.
- **ReAct (Reasoning and Acting)**: prompting framework that structures agent behavior as question → reasoning → action → observation cycles, improving interpretability and accuracy on multistep tasks.
- **Cosine similarity**: measures the angle between two embedding vectors to assess semantic closeness — the core metric behind vector similarity search.

## Mental Models
- Treat RAG as **"retrieval that directly influences each generated word,"** distinct from shallow hybrid approaches that merely prepend retrieved text as a static prompt supplement — the depth of integration is what separates true RAG from "search then paste."
- **Fine-tuning vs. RAG**: use fine-tuning when you need deep behavioral/format adaptation baked into weights; use RAG when you need current or proprietary *facts* injected at inference time without retraining (Ch5 vs. Ch6 is a direct decision fork).
- Match the **vector database choice to your actual constraints**: Milvus for raw QPS performance with self-hosting tolerance, Pinecone for managed low-latency simplicity at higher cost, OpenSearch for native AWS integration and hybrid keyword+vector search, FAISS for prototyping/small-scale in-memory use.
- **RAG reduces but never eliminates hallucination** — always pair it with fallback mechanisms (disclaimers, degrade-to-base-model-with-caveat) and access controls on who can write to the vector database (prevents data poisoning).

## Anti-patterns
- **Using RAG for real-time, latency-critical chat without mitigation** — retrieval adds delay; mitigate with caching of frequent chunks or asynchronous Lambda-based prefetching, not by skipping RAG blindly.
- **Embedding mismatch**: comparing embeddings generated by different models/versions (e.g., titan-embed-text-v1 vs. v2) or mismatched dimensions (768 vs. 1024) — always verify `embedding.shape` before comparison.
- **Disabling SSL certificate verification in production** — the book explicitly flags `ssl._create_default_https_context = ssl._create_unverified_context` as acceptable ONLY for isolated demos/dev environments; it opens on-path attack vulnerabilities and must never ship to production.
- **Ignoring data source quality/reputability** — inaccurate or outdated sources directly degrade RAG output credibility; vet sources (e.g., CDC/WHO for medical data) before ingestion.
- **Static knowledge base with no update mechanism** — for domains with frequently changing facts (pricing, regulations), implement incremental re-indexing or event-driven syncing (Kinesis/DynamoDB Streams + Lambda) rather than full re-ingestion.

# Configuring LangChain with Bedrock LLM + embeddings model
llm = Bedrock(model_id="anthropic.claude-sonnet-4-20250514-v1:0",
               client=bedrock_runtime, model_kwargs={'max_tokens_to_sample': 200})

```python
# Document chunking with overlap
loader = PyPDFDirectoryLoader("./data/")
documents = loader.load()
text_splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)
text_to_process = text_splitter.split_documents(documents)
```

```python
# Building a FAISS vector store and running similarity search
vectorstore_faiss = FAISS.from_documents(text_to_process, bedrock_embeddings)
wrapper_store_faiss = VectorStoreIndexWrapper(vectorstore=vectorstore_faiss)

query = "What measures are recommended for monitoring vaccination program effectiveness?"
query_embedding = vectorstore_faiss.embedding_function(query)
matched_documents = vectorstore_faiss.similarity_search_by_vector(query_embedding)
```

```python
# Invoking a Bedrock Agent and streaming the response
client = boto3.client("bedrock-agent-runtime", region_name="us-west-2")
response = client.invoke_agent(
    inputText=input_text, agentId=agent_id, agentAliasId=agent_alias_id,
    sessionId=session_id, enableTrace=enable_trace)

event_stream = response['completion']
for event in event_stream:
    if 'chunk' in event:
        data = event['chunk']['bytes']
        print(data.decode('utf8'))
    elif 'trace' in event:
        print(json.dumps(event['trace'], indent=2))
```

- **What it demonstrates**: the full local RAG pipeline — LangChain + Bedrock LLM/embeddings setup, PDF chunking with overlap, FAISS vector store creation and similarity search, and the separate Bedrock Agent invocation pattern with streaming trace/chunk events.

## Reference Tables

|---|---|---|---|---|
| Focus | Retrieve + generate | Keyword retrieval | Vector-based retrieval | Single model I/O |
| Data freshness | External, up-to-date | Scheduled, can be stale | Frequent re-index, partial | Bound by training data |
| Output | Synthesized, contextual | Doc links/snippets | Doc passages, no generation | Single-format response |
| Best for | QA, chat, doc summarization | Basic website queries | Deep doc matching | Tasks with no external context |

| Weaviate | hybrid search, strong community | resource-intensive at scale | self-hosted only |

## Worked Example
**Vaccine Information RAG system** (CDC + WHO PDFs, local FAISS implementation):
1. **Ingest**: download COVID-19 vaccination program PDFs from CDC/WHO; load via `PyPDFDirectoryLoader`.
2. **Chunk**: `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=100)` — sized to capture full sentences/paragraphs without becoming unwieldy.
3. **Embed**: Titan Embeddings G1-Text v1.2 (25+ languages, 1,536-dim, optimized for retrieval) — chosen for multilingual clinical/scientific text support.
4. **Index**: build a FAISS vector store from the chunked, embedded documents.
5. **Query**: "What measures are recommended for monitoring and evaluating the effectiveness of the vaccination program?" → embedded → `similarity_search_by_vector` retrieves 4 relevant document chunks (e.g., "Immediate Priorities for Immunization Programs Related to Data Reporting...").
6. **Generate**: retrieved chunks augment the prompt sent to Claude Sonnet 4, producing a grounded, current answer instead of relying on the model's static training knowledge.

**Retail Stationery Agent** (parallel worked example, Bedrock-managed knowledge base + agent):
1. Upload `stationery_products.csv` to S3.
2. Create a Bedrock Knowledge Base (Titan Text Embeddings v2, S3 data source, auto-created vector store).
3. Create an Agent (Claude V4, instructions: "act as a customer service representative..."), attach the knowledge base.
4. Invoke via `client.invoke_agent(...)` — query "What questions can you answer?" returns a grounded product list (Pens, Markers, Highlighters, ...) retrieved from the knowledge base, not hallucinated.

**Why it works**: both examples show the same pipeline shape (ingest → chunk/embed → index → retrieve → generate) at two different abstraction levels — fully manual/local (FAISS) vs. fully managed (Bedrock Knowledge Base + Agent) — letting a reader pick the right level of control for their use case.

## Key Takeaways
1. RAG's three-phase pipeline (query embedding → semantic retrieval → generation) uniquely combines retrieval with true synthesis, unlike search engines or plain semantic search.
2. RAG reduces hallucination and staleness but never eliminates it — pair with fallback disclaimers and restrict who can write to the vector database.
3. Vector database choice should match your constraints: Milvus (raw performance), Pinecone (managed simplicity), OpenSearch (AWS-native hybrid search), FAISS (prototyping).
4. Chunk size and overlap are tunable per document type — ~1,000 chars with 100-char overlap works well for technical/medical documents; always verify embedding dimension compatibility across models.
5. ReAct-based multi-turn agents handle complex, planning-dependent tasks; single-turn function-calling agents handle atomic API-backed actions.
6. RAG has real limitations: latency (mitigate with caching/prefetching), data-source availability (internal/proprietary sources still work), data quality (human-in-the-loop validation), scalability (sharding/tiered storage), and security (encryption + IAM least privilege).
7. Never disable SSL certificate verification outside isolated demo/dev environments — it's a serious security anti-pattern even when convenient.
